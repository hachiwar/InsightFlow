**写在前面**

项目包含完整的前后端系统、核心源代码及测试结果。由于涉及项目隐私与数据安全，关于数据的部分和原本源代码不便直接全部公开，**保留了核心实现逻辑的复现可执行代码、优化策略对应的性能提升情况及变化趋势，便于理解这个项目。**

## 项目背景

在企业数据分析场景中，业务人员通常需要频繁进行数据查询、统计与整理。传统数据分析流程依赖固定报表、人工编写SQL或技术人员协助，存在**使用门槛较高、响应效率较低**的问题。

本项目的主要目的是利用大模型的意图理解能力与写代码的能力，实现自然语言驱动的数据查询与分析。**用户通过自然语言即可完成数据库查询、统计分析及结果整理，降低数据使用门槛，提高数据分析效率与业务响应速度。**

> 即：用户通过询问即可完成数据查询、统计分析的过程，无需写代码。

## 与其他Text2SQL项目的区别

目前GitHub上的开源Text2SQL项目大致可以分为四类：

1. **第一类：**以 SQLBot、Chat2DB 为代表的开箱即用型智能问数或数据库客户端，重点是数据源管理、对话问数、权限、可视化和系统集成
2. **第二类：**是以 Vanna、Dataherald 为代表的 Text2SQL 引擎或 SDK，核心是通过数据库 DDL、业务文档、历史 SQL 和 RAG 为大模型补充上下文
3. **第三类：**是以 WrenAI 为代表的语义层或上下文层项目，重点解决业务指标、字段口径、数据模型和治理问题
4. **第四类：**是以 DB-GPT 为代表的 Agentic Data Assistant，通过规划、SQL 或代码生成、工具调用、沙箱执行和报告生成完成更复杂的数据分析流程。

| 类别                   | 代表项目                            | 主要定位                                                   | 典型技术点                                                   |
| ---------------------- | ----------------------------------- | ---------------------------------------------------------- | ------------------------------------------------------------ |
| 智能问数与 ChatBI 产品 | SQLBot、OpenChatBI                  | 面向业务用户，提供可直接部署的自然语言问数系统             | 数据源配置、RAG、术语库、SQL 示例、对话管理、图表展示、权限、Web 嵌入、MCP |
| Text2SQL 引擎与 SDK    | Vanna、Dataherald、Datrics Text2SQL | 为其他应用提供自然语言到 SQL 的核心能力                    | DDL 检索、文档 RAG、历史 Query-SQL 检索、向量数据库、SQL 生成与执行、API |
| 语义层与治理型框架     | WrenAI                              | 在物理数据库 Schema 上建立业务语义和指标口径               | 语义模型、指标定义、表关系、业务上下文、示例、记忆、权限治理、多数据源 |
| Agentic 数据分析平台   | DB-GPT                              | 不局限于 SQL，将 SQL、代码、检索和工具组合为完整分析工作流 | Agent 规划、工作流编排、SQL 生成、Python、沙箱执行、技能调用、报告生成 |
| AI 数据库客户端        | Chat2DB                             | 面向开发人员和 DBA，将 AI SQL 集成进数据库管理工具         | 数据库连接、SQL 编辑器、AI SQL、元数据浏览、查询历史、多数据库适配 |
| 图驱动 Schema 框架     | QueryWeaver 等                      | 利用表关系图或知识图增强 Schema 理解和 Join 推理           | Schema Graph、关系路径搜索、图检索、SQL 生成、API/MCP        |

- 本项目与这些框架相比，核心优势不在于“也使用了 RAG、Agent 或 MCP”，而在于将字段作为统一检索单元，**为关键词召回、向量召回和 Rerank 分别构造不同粒度的 Schema 上下文，并进一步生成可执行 Schema 图、结构化查询计划以及支持错误根因定位的模块级回调闭环**。
- 主要不足则是目前方案偏重Text2SQL推理链路，**在业务语义层、历史 SQL 学习、权限安全、可观测性、产品界面和成熟生态方面，仍落后于已有开源项目**。

**相比现有项目的优势：**

> 本项目的核心优势在于对 Text2SQL 全流程进行了细粒度拆分，并具备较强的**可解释性**。系统能够记录从 Schema 召回、关系图构建、查询计划、SQL 生成到数据库执行和结果校验的完整过程，既便于定位错误，也能够解释最终结果使用了哪些表、字段、关联关系和计算逻辑。因此，本项目更适合复杂 Schema、多表关联、多步骤分析以及对准确性、审计和过程透明度要求较高的企业场景。

| 优势             | 说明                                                         |
| ---------------- | ------------------------------------------------------------ |
| 字段级精细检索   | 以字段为基本检索单元，并结合表信息和数据样例，检索粒度更细   |
| 多阶段检索设计   | 关键词、向量和 Rerank 分别使用不同层次的 Schema 信息         |
| Schema 图构建    | 能补充表关系、关联字段和 Join 路径，适合复杂多表查询         |
| 结构化查询计划   | 使用四元组拆分查询任务，比自由文本 CoT 更稳定、可验证        |
| 模块级纠错       | 能区分 Schema、计划、SQL 和执行错误，并定向回调对应模块      |
| 多数据库扩展性   | 通过数据库标识和 MCP 路由，适合扩展到多数据源场景            |
| 动态意图路由     | 根据问题类型选择数据库查询或直接问答，降低查询开销和响应延迟 |
| 多轮上下文连续性 | 保留近期问题、筛选条件和分析状态，支持追问、修改条件和连续分析 |
| 历史结果复用     | 优先召回用户保存的历史结果，避免重复执行相同或相近查询       |
| 用户可控长期记忆 | 由用户决定记忆内容，降低无关信息、错误信息和敏感信息被自动保存的风险 |
| 可解释性强       | 完整保留 Schema 召回、查询计划、SQL、执行结果和校验日志，可解释结果来源与计算过程 |

**相比现有项目的劣势：**

> 项目当前的不足主要集中在产品化和工程复杂度方面。相比成熟开源项目，我们的方案包含更多检索、规划、执行和校验环节，虽然增强了准确性和可解释性，但也会增加系统延迟、调用成本及工程维护难度。同时，在业务语义治理、历史 SQL 复用、权限安全和可视化方面仍需进一步完善。

| 劣势             | 说明                                                         |
| ---------------- | ------------------------------------------------------------ |
| 产品成熟度较低   | 相比 SQLBot 等项目，权限、前端、部署和运营能力尚不完善       |
| 业务语义层不足   | 缺少指标口径、业务规则和统一语义模型，容易出现 SQL 正确但业务含义错误 |
| 整体链路复杂     | 多次检索、规划、生成和校验会增加延迟、成本和工程复杂度       |
| 错误定位存在误判 | 校验模型可能无法准确判断错误来自 Schema、计划还是 SQL        |
| 安全与治理不足   | 需要补充 SQL 审计、只读权限、行列权限、超时和敏感数据保护    |
