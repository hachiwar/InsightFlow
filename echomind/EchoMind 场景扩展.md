# EchoMind 场景扩展

### 前言

这里提供几个项目扩展的场景，仅供参考‼️ 如果大家有比较好的场景包装也是可以的。那么该怎么包装呢，下面讲一下我自己的一些思路：

不要把 EchoMind 只定义成智能客服，而是把它抽象成企业里的“知识增强型 Agent 平台”。它的底层能力有四个：

第一，RAG 知识库，解决模型不知道企业内部知识的问题。

第二，MCP 工具调用，解决模型拿不到实时业务数据的问题。

第三，多 Agent 编排，解决一个问题跨多个领域的问题。

第四，评测和监控闭环，解决系统上线后不可控的问题。

所以它可以迁移到合同审查、代码审查、数据分析、风控解释、财务报销、供应链异常、API 联调、A/B 实验分析等场景。变的是知识库内容和工具接口，不变的是架构。

### **企业内部制度问答助手**

可以扩展成企业内部制度问答助手。这个场景和客服类似，但用户不是外部客户，而是企业内部员工。

核心问题是制度文档多、版本经常变、员工问法不统一。EchoMind 里的 RAG 知识库可以存制度文档，查询时通过 query rewrite 扩展用户问题，再用 ChromaDB 做语义召回，最后用 LLM rerank 选出最相关制度条款。

Agent Orchestrator 可以按制度领域路由，比如报销 Agent、HR Agent、权限 Agent。遇到“出差报销 \+ 请假审批”这种复合问题，可以并行调用多个 Agent，再合并回答。

这比普通客服更适合面试讲，因为它强调企业知识管理和流程问答，不只是聊天。

**可映射到 EchoMind**

- `knowledge_base`：存制度文档、流程说明、FAQ。

- `IntentRecognizer`：识别报销、请假、权限、安全等意图。

- `AgentOrchestrator`：路由到 HR / Finance / IT Agent。

- `/eval/run`：用标准制度问答集评测回答准确性和忠实度。

### **运维排障助手**

可以做运维排障助手。用户输入不再是普通客服问题，而是“订单服务 P99 延迟升高”“CMS full GC 时间过长”“支付接口 500 增多”。

知识库里存 Runbook、历史故障复盘、报警处理手册、服务依赖关系。系统先识别故障类型，比如 JVM、数据库、缓存、网络、下游服务，再检索相关排障文档。

Agent 可以分成日志分析 Agent、指标分析 Agent、变更分析 Agent。比如一个请求同时涉及“GC 变高”和“接口超时”，Orchestrator 可以并行调用 JVM 排查 Agent 和接口依赖 Agent。

EchoMind 当前已经有工具调用框架，可以把“查日志”“查 Prometheus 指标”“查发布记录”都封装成工具。RAG 提供知识依据，工具提供实时数据，最终 Agent 给出排查路径。

**可映射到 EchoMind**

- MCP Tool：封装日志查询、指标查询、发布记录查询。

- Tool fallback：日志系统不可用时返回降级说明。

- Monitor：根据工具成功率、延迟调整路由。

- LLM\-as\-Judge：评测排障建议是否完整、是否可执行。

### **业务规则解释器**

很适合业务规则解释。比如电商里的价格规则、优惠券规则、会员权益规则，文档里经常有大量条件、优先级、互斥关系和例外情况。

普通关键词搜索只能找到文档，但不能解释“为什么这个 case 命中了 A 规则而不是 B 规则”。EchoMind 可以先检索规则文档，再结合订单、商品、用户会员状态等结构化信息，由 Agent 生成解释。

这里 Agent 不只是回答“是什么”，还要解释“为什么”：命中了哪些条件，哪些条件没满足，下一步应该怎么处理。

如果进一步增强，可以把价格计算、优惠券试算封装成工具。Agent 先调用工具拿到真实计算结果，再用 RAG 找规则依据，最后给出可解释回答。

**可映射到 EchoMind**

- Query rewrite：把“到手价不对”改写成“优惠规则”“会员价”“券叠加规则”。

- Rerank：优先选中最相关规则条款。

- Tool calling：调用价格试算、优惠券校验、会员权益查询。

- Faithfulness 评测：回答必须忠实于规则条款和工具结果。

### **内容运营助手**

可以做内容运营助手，但我不会让它纯靠大模型自由生成，而是结合 RAG 和规则约束。

知识库里存活动规则、品牌规范、历史优秀文案、禁用词和合规要求。用户输入“帮我生成双十一优惠券活动说明”，系统会先检索活动规则和风格模板，再生成文案。

Agent 可以分为规则校验 Agent、文案生成 Agent、合规检查 Agent。生成后再由合规 Agent 检查是否夸大宣传、是否遗漏关键限制条件。

这个场景体现的是“生成 \+ 校验闭环”。不是只写文案，而是保证文案符合业务规则。

**可映射到 EchoMind**

- 多 Agent：生成 Agent \+ 校验 Agent \+ 合规 Agent。

- RAG：注入活动规则和历史模板。

- 评测：用 LLM\-as\-Judge 评估相关性、完整性、合规性。

- 记忆：记录某个运营人员偏好的文案风格。

### **商品知识导购助手**

**适用场景**

用户问“这两款手机有什么区别”“这个耳机适合跑步吗”“预算 3000 买什么电脑”。系统需要结合商品参数、评价、库存和用户偏好回答。

电商导购本质上是“商品知识 RAG \+ 用户意图识别 \+ 工具调用”。

知识库里存商品详情、参数、评价摘要、售后政策。工具层可以查询实时价格、库存、优惠券、用户历史偏好。Agent 根据用户意图判断是参数对比、预算推荐、售后咨询还是优惠查询。

比如用户问“这款相机适合拍视频吗”，系统先检索商品参数和评价摘要，再结合用户用途生成回答。如果用户继续问“有没有券”，Agent 可以调用优惠券工具。

这个场景比客服更偏业务转化，能体现 RAG 不是只能解决售后，也能支持交易前决策。

**可映射到 EchoMind**

- `user_profile`：记录预算、品牌偏好、用途偏好。

- MCP Tool：查询库存、价格、优惠券。

- Agent 路由：参数 Agent、优惠 Agent、售后 Agent。

- 评测：看推荐是否符合预算和约束。

### **合同审查助手**

**场景说明**

企业法务经常需要审查合同，比如采购合同、服务协议、保密协议。合同条款长、风险点分散，人工逐条检查效率低。



可以做合同审查助手。它不是替代法务做最终判断，而是帮助法务快速定位风险条款。

知识库里可以存公司合同模板、历史审查意见、法务红线、常见风险条款。用户上传一份合同后，系统先按条款切分，再检索相似模板和风险规则。

Agent 可以分成条款解析 Agent、风险识别 Agent、修改建议 Agent。比如发现付款周期过长、违约责任不对等、数据使用条款缺失，就把对应条款、风险原因和建议改法列出来。

这个场景能体现 RAG 的专业知识约束：模型不能凭空编法律意见，而是要引用公司制度和模板条款。

**可映射到 EchoMind**

- `knowledge_base`：存合同模板、法务规则、历史审查意见。

- Query rewrite：把“付款风险”扩展成“付款周期、逾期责任、验收条件”。

- Rerank：优先选中相似条款和风险规则。

- LLM\-as\-Judge：评估审查意见是否完整、是否引用依据。

### **代码库问答与代码审查助手**

**场景说明**

大型项目里，新人经常不知道某个接口在哪里、某个字段怎么流转、改一处代码会影响哪些模块。



可以做代码库问答和代码审查助手。它面向研发，而不是客服。

知识库里存项目文档、接口说明、架构图、代码片段索引、历史 PR 记录。用户问“订单状态字段在哪里更新”“这个接口为什么要加分布式锁”，系统先检索相关代码和文档，再生成解释。

如果接入工具，还可以调用 Git 工具、CI 工具、单测工具。比如用户提交一个 PR，Agent 可以先分析变更文件，再检索相关模块说明，最后给出潜在风险和建议测试点。

这和 EchoMind 的结构很接近：RAG 找上下文，工具查代码和测试结果，Agent 负责总结和审查。

**可映射到 EchoMind**

- MCP Tool：封装 `git diff`、单测、代码搜索、CI 状态。

- Agent Orchestrator：路由到代码解释 Agent、测试建议 Agent、风险审查 Agent。

- Memory：记录某个研发正在看的模块，支持多轮追问。

- Eval：用历史 bug 或 PR 评测审查建议命中率。

### **招聘简历筛选助手**

**场景说明**

HR 或面试官需要从大量简历中筛选候选人，判断经历是否匹配岗位要求，并生成面试问题。





可以做简历筛选和面试题生成助手。知识库里存岗位 JD、职级标准、面试评价维度、历史优秀候选人画像。

候选人简历上传后，系统先抽取技能、项目、实习、教育经历，再和岗位要求做匹配。Agent 可以输出匹配点、风险点、需要追问的问题。

比如岗位要求 Java 后端、Redis、高并发，系统会定位简历里相关经历，并生成针对性追问：“你这个 Redis 分布式锁为什么要用 Lua 保证原子性？”。

**可映射到 EchoMind**

- Entity extraction：抽取技能、公司、项目、时间、技术栈。

- RAG：检索岗位 JD 和评价标准。

- Agent：生成面试问题和评价建议。

- Eval：用历史面试反馈评估问题质量。

### **培训学习助手**

**场景说明**

企业新人培训、技术培训、产品培训需要大量文档和问答。新人常问“这个系统怎么部署”“某个业务流程是什么”。

**面试官可能问：能不能用于教育或培训？**

**我：**

可以做培训学习助手。知识库里存课程资料、操作手册、FAQ、考试题库。系统根据用户问题检索资料，并结合用户学习历史给出解释。

和普通问答不同的是，它要有学习路径和测验能力。比如新人问“我怎么理解缓存穿透”，系统不只是回答定义，还可以根据他之前学过的内容，推荐下一步学习“缓存击穿、缓存雪崩、布隆过滤器”。

**可映射到 EchoMind**

- Memory：记录学习进度和薄弱点。

- RAG：检索课程资料。

- Agent：讲解 Agent、出题 Agent、答疑 Agent。

- Eval：评测回答是否适合当前学习阶段。

### **医疗导诊与报告解释助手**

**场景说明**

患者拿到体检报告或症状描述后，不知道应该挂什么科、指标异常代表什么。系统可以辅助解释，但不能替代医生诊断。



医疗场景可以做导诊和报告解释助手，但必须强调安全边界。

知识库里存公开医学科普、医院科室说明、检查项目解释、就诊流程。用户输入症状或报告指标，系统先检索相关科普，再给出可能就诊科室和注意事项。

它不能做确诊，也不能给处方。回答必须提示“仅供参考，最终以医生诊断为准”。如果出现胸痛、呼吸困难、意识不清等高危症状，要触发紧急就医提示。

**可映射到 EchoMind**

- IntentRecognizer：识别导诊、报告解释、紧急症状。

- RAG：引用权威医学科普和医院流程。

- Escalation：高危症状触发升级提示。

- Judge：检查回答是否越权诊断。

### **财务报销审核助手**

**场景说明**

企业报销涉及发票、预算、差旅标准、审批流程。员工提交报销后，经常因为材料缺失或标准不符被退回。



可以做财务报销审核助手。知识库里存报销制度、差旅标准、发票要求、审批流程。工具层可以查询员工部门、预算、发票 OCR、历史报销记录。

Agent 可以先检查材料完整性，比如是否有发票、合同、付款截图；再检查金额是否超过标准；最后给出退回原因或补充材料建议。

这类场景强调“规则检索 \+ 结构化校验”。大模型不负责最终审批，只负责解释规则和生成审核建议。

**可映射到 EchoMind**

- RAG：检索报销制度。

- Tool：发票 OCR、预算查询、审批状态查询。

- 多 Agent：材料检查 Agent、规则校验 Agent、话术生成 Agent。

- Eval：统计退回原因识别准确率。

### **供应链异常处理助手**

**场景说明**

供应链里经常出现缺货、延迟发货、仓库爆仓、物流异常。运营需要快速判断原因和处理方案。



可以做供应链异常处理助手。知识库里存履约规则、仓储流程、物流异常处理规范、供应商 SLA。工具层查询库存、订单、仓库状态、物流轨迹。

用户问“为什么这个订单还没发货”，系统先查订单状态、库存、仓库、物流，再检索履约规则，最后解释原因，比如库存不足、仓库拣货延迟、地址异常、物流揽收失败。

这个场景强调多工具协同，因为答案不能只来自文档，还需要实时业务数据。

**可映射到 EchoMind**

- MCP Tool：订单、库存、仓库、物流查询。

- Orchestrator：订单 Agent、库存 Agent、物流 Agent 并行处理。

- RAG：履约规则和 SLA。

- Monitor：监控工具延迟和失败率。

### **产品需求评审助手**

**场景说明**

产品经理写 PRD 后，研发、测试、设计需要评审需求是否完整、边界是否清楚、是否有历史类似方案。



可以做产品需求评审助手。知识库里存历史 PRD、需求评审记录、技术方案、埋点规范、测试规范。

用户上传 PRD 后，系统可以检查几个方面：目标是否明确、流程是否闭环、异常状态是否覆盖、权限和风控是否考虑、埋点是否完整、是否有历史类似需求。

Agent 最后输出评审清单，而不是直接说需求好坏。

**可映射到 EchoMind**

- RAG：检索历史类似需求和规范。

- Agent：业务流程 Agent、技术风险 Agent、测试用例 Agent、埋点 Agent。

- Memory：记录某个项目的评审上下文。

- Eval：用历史评审问题看召回率。
